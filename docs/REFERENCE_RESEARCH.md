For presentation, adopt [moreHUD Inventory](https://github.com/ahzaab/moreHUDInventory/tree/68718eeb1698) for Scaleform item-card binding, [SKSE Menu Framework 3](https://github.com/QTR-Modding/SKSE-Menu-Framework-3/tree/ff6b9d0cc313) for blocking versus nonblocking overlay-input separation, and [Skyrim Souls RE](https://github.com/Vermunds/SkyrimSoulsRE/tree/280fe1afb6aa) for careful menu pause-count/background handling and active Sleep/Wait protection. Adopt [Integrated Magics](https://github.com/SkyDwemerForge/Integrated-Magics/tree/a5b9b90493ec) for distinct cast-start, interrupt, charge, animation-event and shout-equipment seams; reject any direct hook-offset reuse until the installed 1.7.104 ABI is validated. These projects have different runtime targets/licenses; none was built or installed in either game.

Reviewer A and Reviewer B independently reviewed physics, drops, ragdolls, inventory and UI read-only. Both identified disabled active-body correction, incomplete world-drop identity/pickup, bool-only death relay, and menu state gaps. Reviewer A additionally flagged negative unmatched inventory deltas, base-ID-only equipment matching, absent `IsAmmo` in equipment notify, and a subtitle `TopicFormId` relay omission; direct source checks confirmed those *code paths*, not an in-game failure. Reviewer B cautioned that current physics-body hooks and offsets remain probes. No production/runtime behavior was changed in this research pass.

The second Reviewer A/Reviewer B read-only reviews completed. Both found graph/pose transport without production pose apply, a missing rig/behavior compatibility gate, load-transition gaps, disabled melee target/hit handlers, concentration/projectile-biased spell sync, and no shout-fire/cooldown authority. Direct source review additionally confirmed Reviewer A's higher-priority finding: `RequestHealthChangeBroadcast` is relayed by the server without owner/epoch checks; the server subtracts `DeltaHealth` while local damage events are negative and receivers add the delta, so damage moves the server's cached health in the wrong direction. Server projectile and magic relays likewise do not check sender ownership. `MagicService::OnNotifySpellCast` dereferences a looked-up actor without a null guard. These are code findings, not paired-game observations. Reviewer B's statement that no native voice hook exists is **incorrect for this fork**: `Actor.cpp::HookSpeakSoundFunction` records/mutes native voice and `CharacterService` replays its filename; that still does not establish synchronized cue start, lipsync or music. No code was changed to fix these findings.

## Character-creator input trial (2026-09-23)

- [CommonLibSSE-NG RaceSexMenu](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/include/RE/R/RaceSexMenu.h) identifies Skyrim's native creator as a paused menu. [SKSE input structures](https://github.com/ianpatt/skse64/blob/master/skse64/GameInput.h) distinguish player controls from menu controls, so `bBlockPlayerInput` alone does not prove a menu-input failure. This remains a scoped causal trial, not a confirmed fix.
- In the paired native creator, the follower showed the finish confirmation but its rendered cursor and selection remained frozen despite a successful desktop child click. A requested native `game_snapshot` reported `controls.blocked=true`, the RaceSex menu open, a foreground 2560x1440 window, and a still-advancing world tick. The capture image is 2048x1152, so screenshot pixels are not client click coordinates; testing the scaled click still did not advance the dialog. The host had previously advanced its native confirmation with an external desktop click.
- The client now releases the follower's party-owned player-input block only while its native RaceSex menu is visible in an active, post-barrier shared-campaign epoch with the overlay inactive, then restores the block on close. Camera authority is based on party phase instead of that local input bit; CameraService already suppresses host-camera writes during RaceSex. This build still requires a fresh paired validation before calling the creator pass fixed or claiming a ready queue.
- [Microsoft's WM_NULL documentation](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-null) permits a `SendMessageTimeout` responsiveness round trip. The test-only key helper now forks a child so the game's pipe/WndProc handler can return, waits for that round trip, and rejects overlapping child actions. Reviewer A and Reviewer B independently warned that helper launch success is not game input completion, so every action must be followed by an observed native menu transition; the helper trace records whether it reached input injection.
- The fresh two-PC trial with client hash `F563497B...` reached both native creators. The follower's `controls.blocked` changed to `false` while RaceSex was open, but a correctly scaled synthetic click still left the confirmation modal open and its rendered cursor unchanged. Thus the scoped release is confirmed to change the flag, **not** to fix automation or creator progression. The current session is left at the modal for further study.
- Read-only native input-poll counters were then added. A fresh paired run with client hash `0AD8EBD3...` again reached the follower's RaceSex confirmation. At that modal, `overlayActive=false`, `directInputSuppressed=false`, and all 24,669 sampled native input-poll calls had been forwarded, with zero skipped for focus, overlay, or cooldown. After the helper queued a click, the modal remained open and all 26,221 input polls were still forwarded. This rules out the overlay and top-level native poll gate as the proximate cause. It does not establish whether the synthetic events reached DirectInput, raw input, Scaleform mouse state, or the MessageBox callback. The next low-risk diagnostic is to count DirectInput keyboard/mouse events and read native menu GFx cursor state before implementing any test-only injection. [Microsoft's DirectInput buffered-mouse documentation](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416239%28v%3Dvs.85%29) explains why client-coordinate clicks cannot simply be inserted into its relative mouse event stream.

## Cinematic actor spawn probe (2026-09-23)

- Live stage-75 capture before restarting (`authority-20260923-161250.json`) sampled both PCs one millisecond apart: 21/25 same-tick host-owned actor pose packets and 21/25 visual packets matched checksums, but 0/12 overlapping rendered skeletons/evaluated poses matched. A five-second follower-only `set_visual_pose_apply` trial (`-161600.json`) was turned off immediately; it applied **zero** bones and did not change the 83/134 sampled render-local matches. Only 1/31 tracked follower actor graph holders had a callback in the prior 200 ms, although global graph callbacks continued. Local `VisualPoseMailbox::InspectPostGraph` is invoked from the graph hook, so packet integrity does not imply visible application when that hook is absent for a remote actor. [CommonLibSSE-NG `NiAVObject::Update`](https://raw.githubusercontent.com/CharmedBaryon/CommonLibSSE-NG/main/src/RE/N/NiAVObject.cpp#L221-L226) provides a native world-transform propagation seam after local transforms are changed, but it is not yet proven safe on this runtime or callback thread. Next trial should invoke the existing lock/generation-guarded mailbox once per remote actor on the game update path *only when opt-in enabled*, then measure applied bones, callback cost, and render readback; do not enable by default until a paired visual and performance result supports it.

- Follow-up source check: [CommonLibSSE-NG `Actor::GetMount` and `IsOnMount`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/A/Actor.cpp) distinguishes a native rider-horse link from a queued package and an interaction extra. In this codebase, `Utils::GetByServerId` resolves a current entity/form, but mount queue state retains only server IDs and has no removal-time cleanup. The sustained-AI trial failed, so the next safe change is to expose *which* rider/mount server IDs are pending, their current form/3D generation, and native link; remove queue entries when either network actor is explicitly removed; and disable the ineffective remote-AI exception by default. This preserves diagnostic leverage while preventing a stale server relation from running remote AI indefinitely. A future authoritative mount presenter needs real source dismount events and a validated native seating path; this cleanup is not that presenter.
- Local server source inspection finds `OnCharacterRemoveEvent` destroys a character without clearing any other character's `MountedOnServerId` referencing it. Since `Serialize` sends that field in later spawns, a destroyed horse can be resurrected as a stale rider-to-horse relation on another client. Clear those references before destroying the horse; the existing `NotifyRemoveCharacter` tells clients to clear pending relations involving that server ID. Do not treat transient local 3D removal as a network removal: leveled-NPC reconciliation can disable/re-enable an actor without invalidating its server identity.
- [The Skyrim `Actor.psc` native API](https://github.com/Amelinyaa/SKSE/blob/master/Data/Scripts/Source/Actor.psc) documents `SetVehicle(ObjectReference)` as attach/detach for horses, carts and other vehicles; it is a potentially more direct general engine seam than `InitiateMountPackage`. This is only a Papyrus declaration, not a verified native binding or proof that it establishes a seated horse animation. Do not call it in the patch until its actual AE implementation/signature and paired effects have been inspected.
- Fresh paired build `0C163803...` showed at MQ101 stage 15 that two host riders had nonzero native `GetMount` links while the follower had **zero mount notifications** (`authority-20260923-160729.json`). The cinematic can establish mounted state without calling the hooked `InitiateMountPackage`, so event-only authority can never cover it. Following the [CommonLibSSE-NG native `GetMount` binding](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/A/Actor.cpp), poll host-owned actors' actual mount relations at a bounded cadence, resolve rider/mount current server identity and ownership epochs, send changes plus periodic idempotent retries, and send an explicit zero relation after a short absence debounce. On the server, validate zero-relation requests against the rider's ownership epoch without requiring a mount entity, then publish `NotifyMount(0)`; do not reinterpret missing 3D as dismount. This is a general actor-state source path, not an intro script patch. It still does not solve follower native seating; measure that separately.
- Host-native polling build `FDAFC0E8...` passed 135 protocol assertions and ran paired. At `authority-20260923-161942.json`, host rider form `0x198BC` (server ID 32) reported native mount form 337905 (horse server ID 28). The follower already had the durable rider32→horse28 relation from its spawn snapshot, with both actors' 3D present, but native `GetMount` remained zero; 34 package rejections and zero confirmed seats. By `-162128.json`, it had 113 rejections and 17 package starts with no seat. This confirms the source relationship now reaches the server/late-spawn follower; it does **not** make the remote actor ride. Receiver lifecycle/seating remains a distinct unsolved engine problem. A zero-notification count is not contradictory because spawn snapshots carry the persistent relation.

- The user's floating heads and standing riders occur **while cinematic NPCs spawn**, not after the intro. [CommonLibSSE-NG `TESObjectREFR::Get3D`/`GetBiped`](https://github.com/alandtse/CommonLibSSE-NG/blob/ng/src/RE/T/TESObjectREFR.cpp) confirms scene 3D and biped state are distinct native surfaces; [its `Actor::GetWornArmor`/`GetMount` implementations](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/A/Actor.cpp) expose equipped-state and actual mount-state checks. Local `WaitingFor3D` code currently assumes first root node means ready and then sets inventory, while mount code treats a successful package start as applied. A read-only paired spawn-window probe will compare root-node presence/children, worn-armor count, and native mount relation before changing the actor visual lifecycle. These are diagnostics, not a fix.
- Paired spawn capture `authority-20260923-154732.json` at MQ101 stage 15 found both riders mounted natively on the host and **neither** mounted natively on the follower, although the follower counted two successful mount-package initiations. Both riders had root nodes with seven children and three worn armor entries on each PC. A third NPC briefly had four host vs two follower worn armor entries; by `-154748.json` that count converged. The host/follower mount mismatch persisted. This rejects the assumption that successful `InitiateMountPackage` equals seated state and indicates a separate transient inventory/equip race. Local `HookActorProcess` returns immediately for all remote actors, preventing any remote mount package from advancing. The next narrowly scoped trial permits native actor processing only while a remote rider is awaiting a server-authoritative mount and retains the pending relation until native `GetMount` confirms seating. It may still let native AI run during that transition; paired visual/quest parity must be rechecked, and no full fix is claimed.

Therefore a momentary seated state is not durable under the old remote-AI suppression. The next trial keeps native actor processing enabled for the server-reported mounted interval and retains the relation for validation. Dismount source updates are not yet implemented, so this remains an experiment rather than a general solution.
- Sustained-processing trial `D5DAFFD8...` did **not** resolve seating. At MQ101 stage 15, `authority-20260923-155600.json` showed two pending follower mount relations, two native package starts, zero confirmed seats, 109 missing-3D retries and 16 package rejections; `-155615.json` rose to 246 missing-3D retries and 46 rejections. Later source/follower snapshots both had 3D for rider server ID 6 and horse ID 8, yet only the source rider's native `GetMount` pointed to that horse. A separate stale pending relation (rider 11/mount 14) outlived its rider entity. This disproves a simple remote-AI-tick-only fix. Next investigation must correlate each pending server relation with actor generation/3D readiness, validate actual mounted state continuously, clear stale relations on removal/dismount, and inspect native package rejection reasons before shipping this path. The current deployed build is experimental and parity remains red.

## Native physics parity timing trial (2026-09-23)

- [CommonLibSSE-NG's animation graph manager holder implementation](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/I/IAnimationGraphManagerHolder.cpp) resolves the native `UpdateAnimationGraphManager` call (AE ID 32899); the existing local hook around that call already observes the post-update skeleton. Code inspection found its `VisualPoseMailbox::InspectPostGraph` invocation was accidentally restricted to the one diagnostic watched holder. That makes received host pose packets inert for every other remote NPC even when the opt-in application is enabled. The next patch moves the mailbox invocation outside the watched-holder gate, while retaining the watched-only expensive checksum probe and default-off pose writes. This addresses coverage, not correctness or cadence; paired validation is required.
- Paired build `9284AF2F...` confirmed that wider hook coverage: follower mailbox inspections rose from 3,258 to 19,135 between `authority-20260923-141946.json` and `-142000.json` while both clients stayed alive and the game loop stayed near 60 Hz. The opt-in all-actor write trial (`-142024.json`) applied 805,127 bones in 10,258 frames without a reported write failure, but its last callback took 12,475 µs and its last source frame was 938 ms old. Pose writes were explicitly turned off immediately. This is not a usable presenter: it needs source-tick presentation, stale cut-off, interpolation, and a cheaper validated native write path before enabling by default. Reviewer A independently found the same watched-holder restriction and proposed a bounded presenter; its suggested lip-sync path remains untested, so only the source-verified coverage fix was adopted.
- [CommonLibSSE-NG's `BSFaceGenAnimationData`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/include/RE/B/BSFaceGenAnimationData.h), [`BSFaceGenNiNode`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/include/RE/B/BSFaceGenNiNode.h), and [`BSFaceGenKeyframeMultiple`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/include/RE/B/BSFaceGenKeyframeMultiple.h) show a separate phoneme keyframe array on the face node. This supports a read-only paired lip-motion probe before attempting authority writes; skeletal bone packets alone cannot establish mouth parity. The runtime node offsets and line-to-face timing have not yet been validated on the installed executable.
- [CommonLibSSE-NG's `NiAVObject` source](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/N/NiAVObject.cpp) exposes native transform propagation, and [Active Ragdoll's native node code](https://github.com/adamhynek/activeragdoll/blob/master/src/utils.cpp) directly writes a node's local transform before native update. The current mailbox uses one `WriteProcessMemory` call per bone in our *own process*; its measured 12.5-ms post-graph callback is unsuitable for multiple NPCs. A guarded direct in-process transform assignment under the existing graph lock is a justified opt-in performance trial, with the same graph/root generation checks, native write exception guard, and paired readback. It does not by itself establish render or physics parity. A receipt-age cutoff is also needed to stop presenting a frozen old frame while the current pose producer remains sparse.
- Paired build `02CC37A1...` exercised that opt-in path. In `authority-20260923-142639.json`, the follower applied 124,679 bones in 1,712 frames with zero write failures; the last callback took 145 µs rather than the previous 12,475 µs. Its game-loop entry gap remained ~17 ms. The 200-ms receipt-age gate skipped 9,208 old-frame applications. Shared-tick capture `-142654.json` still had 0/12 exact evaluated-pose and skeleton matches, but several NPCs' 11-12 sampled render-local bones matched while the moving roots differed 52-1,424 units. The actor stream itself only captures two poses per 100-ms movement packet. [The project's transport send path](../Code/client/Services/Generic/TransportService.cpp) allocates a 64-KiB client packet buffer, while [server movement fan-out](../Code/server/Services/CharacterService.cpp) sends on a 20-ms loop. A bounded 4-pose/50-ms producer trial stays well below the client packet buffer for typical 99-bone actors, but must be paired-tested for bandwidth, frame cost and stale skips before adopting. It is not a claim of five-player capacity.
- Paired producer build `AF56DA0F...` kept the host/follower game loops near 60 Hz and published 2,270 follower pose frames by `authority-20260923-142957.json`, but 7,986 post-graph callbacks still skipped frames outside the 200-ms receipt window. Shared-tick capture `-143011.json` remained 0/12 exact skeleton matches and 116/133 sampled render-local bone matches (compared with 123/133 in the earlier slower-stream capture, at a different scene moment). The observed 5120x1440 overlay and correctly resized text prove that the overlay texture and 2D viewport are updating. ## Windows Snap and live window resizing

- [Microsoft: Support snap layouts for desktop apps on Windows 11](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-snap-layout-menu)
  - Standard Win32 caption/maximize behavior supplies Win+Z Snap Layouts. Apps
    must accept the selected zone size rather than immediately enforcing a
    previously stored size.
  - Microsoft recommends supporting a minimum width no larger than 500
    effective pixels; this project accepts windowed client sizes down to 330.

- [Microsoft: DXGI overview and handling window resizing](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/d3d10-graphics-programming-guide-dxgi)
  - `WM_SIZE` is the authoritative notification for a resized HWND. The
    application should rebuild its swap-chain buffers/render targets for the
    new client area rather than moving the HWND back to an old resolution.

- [SSE Display Tweaks `window.cpp`](https://github.com/SlavicPotato/SSEDisplayTweaks/blob/master/SSETweaks/window.cpp)
  - Uses normal Win32 window messages and only calls `SetWindowPos` for an
    explicit centering/fullscreen operation. It does not continuously enforce
    the configured dimensions after an external window resize.

Direction for this project: distinguish programmatic display-mode transitions
from external `WM_SIZE` events. A Windows Snap operation becomes the new
windowed client size, cancels any stale display preview, and is persisted rather
than reverted.

The same Snap workflow also requires returning ownership of the shared Windows
pointer while the shell UI is open:

- [Microsoft `ShowCursor`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showcursor)
  - Cursor visibility uses a counter, so a single show call does not reliably
    undo a game's earlier hide calls; increment until the result is nonnegative.
- [Microsoft `ClipCursor`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-clipcursor)
  - Microsoft explicitly requires an application to release cursor confinement
    before relinquishing control to another application.

Direction for this project: on either Windows-key press, release capture and
clipping, normalize `ShowCursor(TRUE)`, and keep the system arrow active for the
Snap chooser. Reclaim it only when focus or a click returns to Skyrim.

- [CommonLibSSE-NG `UI3DSceneManager.cpp`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/U/UI3DSceneManager.cpp)

- [Skyrim Ultrawide RaceMenu Fix](https://github.com/theosw/SkyrimUltrawideRaceMenuFix)

Direction for this project: after a renderer target rebuild or accepted Win32

## Complete live Scaleform reinitialization after resize

- [CommonLibSSE-NG `BSScaleformManager.cpp`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/B/BSScaleformManager.cpp)
  - `LoadMovie` initializes every movie from `BSGraphics::State`, then applies
    its scale mode, safe rectangle, full framebuffer viewport, advances frame
    zero, and calls `IMenu::RefreshPlatform`.
- [CommonLibSSE-NG `GFxMovieView.h`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/include/RE/G/GFxMovieView.h)
  - Confirms `SetViewport`, `SetViewScaleMode`, and `NotifyMouseState` are
    per-movie state. Updating Main Menu alone cannot resize the independent
    Cursor Menu movie.
Direction for this project: a runtime resolution transition synchronizes
`BSGraphics::State`, reapplies the viewport and existing scale mode to every
live Scaleform movie, calls each changed menu's `RefreshPlatform`, and then
reapplies the Mist Menu camera FOV. This mirrors the relevant
parts of movie startup and prevents Main Menu, Cursor Menu, and UI3D from each
retaining a different prior resolution.

The extracted 1.7.104 `startmenu.swf` ActionScript and Reviewer B's consolidated
`docs/reverse-engineering/UI_SCALEFORM_MIST.md` add an important constraint:
`StartMenu::InitExtensions()` runs once, locks the menu root bottom-right and
`Logo_mc` bottom-left using `Stage.visibleRect`/`Stage.safeRect`, and has no
resize listener. A viewport update therefore cannot reproduce clean-start
widescreen placement. A live experiment that queued native Hide/Show messages
for Mist Menu and Main Menu recreated the shells but did not replay the native
callbacks that populate the menu, leaving it blank; that approach was rejected.
The selected direction is a resize entry point inside the patched SWF that
reflows the existing clips without destroying menu state. The separate
`MenuCursor` singleton (CommonLibSSE-NG ID `403551`) is also resized because
replacing only Cursor Menu's movie viewport leaves its native clamp bounds at
the preceding window size.

Implemented direction: the derived `startmenu.swf` keeps the original
`MovieClip.Lock` behavior but moves the three vanilla anchor calls into an
idempotent `SkyrimSeamlessRefreshLayout` method. A persistent frame watcher
compares the current `Stage.visibleRect` dimensions to the last applied values
and invokes that method only after a real size change. This avoids undocumented
native `GFxMovieView::Invoke` offsets and retains the populated menu instance.
The installed SWF was exported again after compilation to verify that the
watcher and reflow method survived bytecode import.

## Live options behavior

- Skyrim's extracted `quest_journal` `SystemPage.as` sends `OptionChange` on
  each slider/toggle change and reserves `SaveSettings` for persistence when
  leaving the page. This establishes the native UX target: changes are live,
  while saving is a separate operation.
- [SSE Display Tweaks configuration](https://github.com/SlavicPotato/SSEDisplayTweaks/blob/master/SSETweaks/SSEDisplayTweaks.ini)
  documents that its game-setting adjustments are in-memory rather than INI
  writes, supporting the same separation between runtime values and persisted
  launch configuration.

Direction for this project: every control updates the game's live settings
collection immediately. Non-display changes are persisted immediately as well.
Display mode, monitor, and resolution become live immediately but retain a
15-second keep/revert transaction because an unsupported mode can obscure the
confirmation UI. Confirmation persists the already-live state and must not
perform a second renderer rebuild.

Runtime testing showed that INI-collection writes alone do not drive Skyrim's
cached audio mixer. CommonLibSSE-NG documents `BGSSoundCategory`'s
`BSISoundCategory` interface at `+0x30` and virtual slot 3 as
`SetCategoryVolume(float)`, which is used for footsteps, voice, music, and
effects. Executable tracing showed that master volume is not a sound category:
native `OptionChange` case 27 updates separate live audio-manager state. The
implementation therefore invokes that verified native case for master volume
instead of treating a default-object category as equivalent.

The 1.7.104 executable's `OptionChange` callback was independently traced at
RVA `0x9AB260` (Address Library ID `53310`). Switch case 13, the Brightness
entry after the 13 gameplay entries, maps the slider through Skyrim's gamma
minimum/maximum and writes the live gamma value at RVA `0x20D0348` (Address
Library ID `388988`). The implementation writes ID `388988` explicitly after
updating `fGamma:Display`, reproducing the renderer-facing part of the native
callback without fabricating Scaleform callback arguments.

Microsoft's XAudio2 documentation establishes a separate constraint for output
device switching: the mastering voice represents the output endpoint, only one
mastering voice may exist per XAudio2 instance, and it cannot be destroyed while
source or submix voices remain. Therefore an output-device dropdown must use a
verified Skyrim audio-subsystem teardown/rebuild or process-route migration; it
must not merely store a device name and claim a live switch.

## Controller navigation for the CEF options menu

- [Microsoft: Getting Started With XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput)
  confirms that `XInputGetState` exposes the digital D-pad, sticks, and face
  buttons directly, independent of a game's higher-level menu bindings.
- [CommonLibSSE-NG `InputMap.cpp`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/SKSE/InputMap.cpp)
  confirms Skyrim's gamepad input is represented by the same XInput button
  masks, including the four D-pad directions.
- [Xinput-Modkey-SE](https://github.com/ike9000e/Xinput-Modkey-SE) is prior
  open-source Skyrim SE work that polls XInput and translates controller state
  into keyboard-style inputs without replacing Skyrim's normal configuration.

Direction for this project: while the modal CEF overlay owns input, poll the
first connected XInput controller and translate D-pad/stick navigation plus
A/B into CEF keyboard events. This avoids depending on Skyrim forwarding input
to a non-Scaleform browser. Dropdowns are made keyboard-focusable and handle
left/right plus confirm explicitly; visible focus outlines make controller
position unambiguous. Skyrim's own device poll is suppressed for the lifetime
of the modal overlay so the translated press cannot also activate the native
main menu underneath it. Win32 focus loss, rather than the Windows-key event,
is the authoritative signal for releasing cursor clipping and restoring the
visible desktop cursor.

Follow-up runtime testing established that device ownership must be dynamic,
not controller-exclusive. D-pad up/down are delivered as arrow keys: the
settings panel uses them for focus movement, while an open dropdown consumes
them to move its highlighted option and A confirms it. Physical raw-mouse
movement immediately restores the browser pointer, and subsequent controller
navigation hides it again. `WM_ACTIVATE/WA_INACTIVE` is included in desktop
cursor release because opening the Windows shell can deactivate Skyrim without
delivering `WM_KILLFOCUS` or `WM_ACTIVATEAPP(FALSE)` first.

The final Win32 correction treats `GetForegroundWindow() != SkyrimHwnd` as
authoritative during `WM_SETCURSOR` and returns `TRUE` through the outer
renderer hook. Returning zero after setting the arrow allowed Windows/Skyrim
to treat the message as unhandled and hide it again. An automated test now
deactivates the real game HWND, moves the pointer over its client area, and
confirms `CURSOR_SHOWING` with the standard arrow handle.

## Durable shared-campaign persistence

- [SkyMP server configuration](https://github.com/skyrim-multiplayer/skymp/blob/main/docs/docs_server_configuration_reference.md)
  and the locally pinned MIT `viet` storage interfaces demonstrate a
  server-owned database boundary with replaceable database drivers and
  asynchronous batched upserts. This supports the core decision that shared
  world truth must outlive both clients and the server process. The current
  slice adopts the durable server boundary, but not SkyMP's whole ChangeForm
  schema: Skyrim SE Multiplayer needs ordered cross-domain transactions and a
  common checkpoint watermark for quests, lifecycle, inventory, references,
  and later save projection.
- [CommonLibSSE serialization example by Ryan McKenzie](https://gist.github.com/Ryan-rsm-McKenzie/b1c1e04f95f471c200834b6ac7ebd962)
  demonstrates SKSE co-save records and versioned save/load callbacks. This is
  the correct later location for small client projection metadata such as
  campaign ID, player ID, and last applied revision. It is deliberately not
  used as the canonical campaign database: a follower's missing or stale
  co-save must be recoverable from the server ledger.
- [Elden Ring Seamless Co-op FAQ](https://ersc-docs.github.io/faq/) documents
  host-based progression and warns that session event flags persist into each
  participant's local save. Its separate `.co2` profile informs the product
  behavior, while raw host-save copying is rejected for Skyrim because an ESS
  also contains player identity, Papyrus VM state, aliases, persistent handles,
  and load-order-dependent data.

Implemented direction: `Code/campaign/CampaignLedger.*` is a SQLite WAL-backed
campaign sequencer with a stable campaign UUID, authority epoch, monotonic
revision, unique transaction IDs, durable journal, and checkpoint watermark.
The server opens it before constructing gameplay services. Authentication now
advertises campaign identity/revision/epoch, and leader quest updates commit to
the ledger before modifying the in-memory quest log or broadcasting. Native
ESS writes remain intentionally out of scope until snapshot/reconnect and save
barrier protocols can prove that all clients are materializing the same
committed revision.

- [SmoothCam's camera implementation](https://github.com/mwilsnd/SkyrimSE-SmoothCam/blob/master/SmoothCam/source/camera.cpp)

  follower camera must apply its buffered host snapshot at this boundary (or a

- The pinned CommonLibSSE-NG headers for
