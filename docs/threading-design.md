# Client frame threading design (read-only review, 2026-10-01)

Scope: SkyrimSE.exe 1.7.104 and the current client tree. This is a proposed migration, not an implemented or in-game validated fix. File references below are to `Code/client/` unless stated otherwise. VA means image virtual address; N is the Address Library ID. No source, build, game, or test run was changed for this review.

## 1. Frame placement: finding 17 is correct, with limits

**Directly checked in the offline decompile:** `sk.cmd fn id:39074` shows `Job_VM_update` at `0x1406E57D0` calling the mod-hooked `SkyrimVM::Update` N53926 (`0x1409D7450`) **before** `TasksToJobs` and the dynamic pre-render list's `Begin`/`Finish`. `sk.cmd callers id:53926` also identifies the inline caller `Main::Update` N36564 (`0x140658870`), plus freeze/pump callers N53930/54006/54015/54020/54025. `sk.cmd fn id:36564` shows a normal-frame job kick N35408 and later render call N36555, followed by join N35409; its paused branch calls N53926 inline. `sk.cmd fn id:35423` confirms the serving thread begins and waits each list, then sets its done event. `sk.cmd fn id:39042` confirms the UI job pumps messages and signals J2; `sk.cmd fn id:39067` enters TES world/cell update N13291. These checks support the finding's thread claim, although the C decompile alone does not establish actual temporal overlap on a given PC.

**Atlas-derived frame ordering:** [main-loop §3–4](C:/Users/mwalt/SkyrimAtlas/systems/main-loop-and-frame-phases.md), [jobs §3](C:/Users/mwalt/SkyrimAtlas/systems/jobs-tasks-and-threading.md), and `graph/frame_phases.tsv` place N39074 in list 3, after actor movement/animation and in a group with ragdoll animation. List 2's high actor update is complete by then. List 3 can overlap the main thread's culling, shadow setup, and `Main::Draw` N36559 (`0x140656E60`); culling itself starts worker jobs. It does **not** overlap list 4's `Job_UI` N39042, list 4's `Job_Cell_animations` N39067 (Havok step N13291 `0x1401A1500`), or lists 5–7, because the frame lists are sequential. The main-thread render frame N36555 (`0x1406565B0`) waits for J2 before menu rendering; J2 cannot occur until list 3 finishes. List 4 UI, process jobs, physics and ragdoll post-physics can overlap later scene rendering. List 6 runs post-process Papyrus functors/task queues and input polling. The main thread joins all seven lists at N35409 (`0x14060EB80`, call `0x14065932F`). In a paused or freeze-time frame no frame lists are kicked; N53926 is inline on the main thread if `gameLoaded` is set. Freeze/overstress callers mean the VM hook is **not guaranteed once per render frame** and can run on another pumping thread. The atlas' [Papyrus VM §2, §6](C:/Users/mwalt/SkyrimAtlas/systems/papyrus-vm-internals.md) also shows script native work may run in this VM job and tasklets; neither a Papyrus call nor `QueuePostRenderCall` implies main-thread execution.

The current hook `SkyrimVM64.cpp:28–45` calls `g_appInstance->Update()` before original N53926, subject only to `!apThis->inactive`; `TiltedOnlineApp.cpp:118–137` calls `World::Update`. `World.cpp:223–263` then runs `PreUpdateEvent`, `RunnerService::Drain`, `UpdateEvent`, and `GameTestService::OnGameThread` in that worker slot. Its duration is **outside the native VM's budget** yet delays list 3 and therefore the UI/physics lists. Existing logs of `PlayerControlSync::Update` on six thread IDs in three seconds are consistent with rotating job workers; the offline schedule proves the slot, not those particular observed IDs. This verifies finding 17's placement and scope. Specific races remain hypotheses until observed.

`HookMainLoop` at `SkyrimVM64.cpp:48–63` wraps N36564. Its lines 50–58 execute **before any native `Main::Update` code**; the preceding frame joined at N35409 and the next frame has not kicked at `0x140658B0F`. This is the main quiet window, with no frame-list worker, culling or render work; persistent IO/audio/task threads still exist. Native direct-access mask N39034 has not yet been set, so native task-queue-aware calls may execute directly. The original at line 60 performs the entire frame. Lines 61–62 execute after join, paused drains and present, except that N36564 can early-out on Alt+Tab. The separate `WorldStateService::HookPhase`, `Services/Generic/WorldStateService.cpp:39–52`, filters the N21873 call's return address `0x1406594AD` (N36564+0xC3D): its `MainThreadUpdate` is also post-join and runs *inside* the original, before `HookMainLoop`'s tail. These are distinct ordering points. [Atlas phase map §10](C:/Users/mwalt/SkyrimAtlas/systems/main-loop-and-frame-phases.md) supplies the inter-frame interpretation; the N36564 decompile and mod wrapper call order were checked here.

## 2. Subscriber inventory

`U` means current `UpdateEvent`, `P` current `PreUpdateEvent`. `Q` means move/keep the engine-facing part in the **main pre-original quiet window**. `T` means a **post-join** sample/apply, where it needs the just-finished simulation. `W` means a bounded worker or non-engine bookkeeping piece can stay away from the main thread **only after an explicit split**; it is not a certification of the entire present callback. No `PostUpdateEvent` dispatcher or subscriber exists in `Code/client` (`rg PostUpdateEvent`); native `CameraService` post-update hooks and `WorldStateService` tail are separate callbacks. All listed `U` callbacks currently inherit the VM hook's worker/paused-main behavior. Registration order is `World.cpp:162–216`, but EnTT connection order is an implementation detail to make explicit where correctness needs it.

## 3. Minimal migration and ordering contract

1. **First correctness cut:** introduce a named `World::UpdateMainFrame` for one gated native-facing slice, called by `HookMainLoop` **pre-original** after the existing main pumps and before `ThisCall(MainLoop)` (`SkyrimVM64.cpp:50–60`). Keep the rest of `g_appInstance->Update()` in `HookVMUpdate` (`:33–35`) temporarily. Gate the new call by `GameVM::Get() && !inactive` and World initialization; compare this gate at both hook points in paused, loading and title-screen states. Use one consumer for each migrated callback: disconnect it from the old `UpdateEvent` before connecting it to the new main-frame event. Leave original N53926 unconditional and preserve its diagnostics. Do **not** move the entire dispatcher in one cut: `CharacterSnapshots::OnMainFrame` produces data consumed by U, while move/Object/loot drains consume U-produced queues from the previous frame. Running new U work after those drains preserves that one-frame handoff; if a service needs same-frame apply, specify and test the changed order. The existing post-original `ObjectService::OnMainFrameEnd` and `HarnessService::MainThreadUpdate` remain at `:61–62`; `WorldStateService` remains at the filtered N21873 tail. Native task-queue affinity may flip when the caller becomes main, so inspect `ShouldUseTaskQueue` N39033 (`0x1406E49E0`) consequences per migrated path.
2. **Make the split explicit in `World.cpp:223–263` and `World.h`:** after the final service moves, a main-thread `UpdateGameFrame(delta)` owns the EnTT registry and *all* `PreUpdateEvent`, runner closures, native-facing `UpdateEvent` and GameTest dispatch, in exactly that order. The former VM call then becomes a bounded pure-value/network tick, or is removed if its remaining work is already done by the transport's own threads. Move transport socket polling/packet decoding and file/updater work to their existing background mechanisms only after those operations produce immutable value messages and never synchronously invoke game/registry subscribers. At the pre-original window, deliver received value packets on main (`TransportService` API at `Services/Generic/TransportService.cpp:291`), then P discovery/lip, runner, U callbacks, GameTest. To avoid changing current semantics silently, test whether current `TransportService::HandleUpdate` U actually receives before its packet consumers; if so, explicitly drain packet delivery before P and document that one-frame timing change. The `entt::dispatcher` and registry remain single-thread owned. A bounded receive budget must defer whole messages in arrival order, with epoch/generation validation; never hold network/mailbox locks while calling engine code.
3. **Explicit service barriers:** packet/epoch changes and queued runner operations → discovery and spawn/assignment → actor value/inventory/magic/camera/quest reconciliation → outbound snapshots. `PreUpdateEvent` remains before runner/U as currently coded; if a packet must create an actor visible to discovery in the *same* frame, add a named packet-delivery stage before P, rather than relying on registration order. Preserve the `UnstuckReset::BeforeCamera → CameraService → UnstuckReset::OnUpdate` order and main-frame `CharacterService::ApplyMoves` before generic Character U. Calendar/party gate changes must precede native N36564's pause snapshot/calendar step. `WorldStateService` post-join sampling stays after all frame lists and after `World::UpdateGameFrame`; its outgoing value queues are then sent next frame. Do not move native graph or Havok step hooks to the generic dispatcher.
4. **Paused, loading, title screen:** pre-original Q runs in paused frames too; paused N36564 calls N53926 inline only when `gameLoaded`, and runs UI/input/task drains inline. Guard every world-mutating service with existing loading/player/cell/3D checks; avoid executing deferred spawns or `CenterOnCell` while `Loading Menu` is open. A pause/menu change made in Q affects the **same** native frame's pause snapshot. `GameVM::inactive` must continue gating gameplay, and its value at main-loop entry needs a paired trace against VM entry before deleting the old gate. The runner currently does not run reliably at the title screen, so keep `SteamLobbyService::PollMainMenuOptions`/title queue and `TransportService::PumpMainMenu` (`Services/Generic/TransportService.cpp:284–288`) independent of gameplay `World::UpdateGameFrame`; route title-screen actions to a specifically named menu queue, not to `RunnerService`, and do not double-pump either menu service. The `bAlwaysActive` write in `TiltedOnlineApp.cpp:131–134` must remain once per applicable frame when moving its caller. N36564 has a second caller N36550 (`0x140654480`) per atlas §2; check whether it occurs during loading before treating every main-loop entry as a gameplay frame. Inactive/Alt+Tab frames receive no `Main::Update`; do not promise a 60 Hz game pump when WinMain sleeps.

The alternative post-join hook at `0x1406594AD` is best for capturing *completed* actor/quest/physics state, and is already used by WorldStateService. Running general actor mutations there would take effect one frame later than pre-original and could race menu/message work between frames; use it only for named post-frame readers or producers. There is no universally safe phase for work which requires a specific native step. For example, actor animation graph changes that must happen after graph update need their existing graph hook or a separate proven phase, not a blanket relocation.

## 4. Risks, validation, performance

The pre-original interval is quiet with respect to the seven frame lists, **not** all threads. Steam/CEF, socket, audio, save/load and engine background threads can still enqueue. Holds/handles must be re-resolved in Q, generation/epoch checked, and no native pointer may cross a value mailbox. Before moving each subscriber, search its thread-ID branches and every nonrecursive lock held across a native call: a path formerly queued from the VM worker may execute inline and re-enter its own hook on the main thread. In particular, audit `ObjectService`'s physics locks and `CharacterService`'s cell-load path. A synchronous `RunnerService` closure can initiate save/load or cell changes before N36564's own save pump; audit those closures and bound total work. Moving the whole dispatcher onto main can trade a race for a hitch. Current world-entry gap counters and VM timing (`World.cpp:223–275`, `GameLoopDiagnostic`) measure the old slot; split counters into Q pre/runner/U/GameTest and VM-original, and label paused frames separately. Avoid interpreting a shorter VM job as total frame improvement.

Before any implementation, add protocol-level tests for arrival order, epoch switch/disconnect, stale actor handles, pause/unpause, loading hold/release, and menu queue routing. After each small cut, run existing harness scenarios on a **paired build**: a full `helgen-intro` from cart through creator/escape (scene, camera, mounted/cart, spawn, lip, quest, death/respawn and checkpoint transitions), then repeated `tower-from-street` checkpoint runs on host and follower (door/cell/quest, inventory/drop, weather, late join/reload). Compare paired captures by authority epoch/tick and in-game observations: same quest/stage/scene progression, player/NPC positions and 3D, camera/control recovery, inventory and corpse/drop identity, no lost packets or duplicate actors, and stable pause/menu behavior. A successful protocol run or a single client trace does not prove the race fixed; claim closure only after the changed build is exercised and the observed paired result confirms it.

Record for each peer and scenario: frame-entry gap **p50/p95/max** (ms), gap counts over 50/100/250 ms, Q pre/runner/U/GameTest duration p50/p95/max, native VM call duration, total `Main::Update` duration, and harness **capture time** p50/p95/max (µs). Compare against the same route/build configuration's before baseline and against the other peer; report max separately with the exact loading/saving context. Existing `docs/REFERENCE_RESEARCH.md` near line 2025 records one earlier non-clean attempt at ~16/31 ms frame-gap p50/p95 on both peers and ~2.8–2.9 s max, capture 130/289/10014 µs host and 140/273/3143 µs follower; a concurrent build makes it diagnostic context, **not** an acceptance threshold. Profile five concurrent players before claiming the initial five-player performance target; two-player correctness is the first gate.

## 5. Rollout in independently testable cuts

1. Document current thread/phase baseline from existing logs and counters, plus a paired unmodified harness capture; no live offset probe is needed (native frame code was read above). Check both modes and main menu.
2. Move only `GameTestService::OnGameThread` test-command drain to the existing Q pre-pump, preserving command order; test damage/add/drop/enable/creator commands and paired no-command baseline. It is gated and low blast radius. Remove its old call at `World.cpp:263` in the same cut.
3. Move P discovery/lip and the runner to Q with explicit owner assertions and a menu queue; verify actor discovery, queued overlay/quest/checkpoint commands, intro and title-screen lobby path. Then migrate one U service family at a time (actor/ref/physics; quest/inventory/magic; camera/controls/UI; diagnostics/transport), retaining the old path only for audited value-only work. Each cut gets protocol tests and paired observations before the next.
4. Once all native-facing subscribers are out of the VM hook, make `World::UpdateGameFrame` the Q owner; remove the gameplay call from `HookVMUpdate`, leaving N53926 and timing. Keep any audited value-only VM tick bounded, or remove it if redundant. Check one game update per actual N36564 frame, VM freeze/pump, paused frames, and absence of native-facing U calls on job-worker IDs. Run full intro and tower checkpoint pair again.
5. Profile and bound Q work, then split immutable packet decode/serialization from main delivery. Compare p50/p95/max frame gaps and capture cost on paired runs; exercise five peers before any five-player performance statement.

## References and independent review

Primary open-source research: [skymp threading issue #653](https://github.com/skyrim-multiplayer/skymp/issues/653) reports game-native calls from its JS worker causing crashes and proposes a game-thread execution boundary; adopt the separation of worker script/network work from native engine operations, not its blocking cross-thread call scheme because this client already has a per-frame quiet hook and should avoid waits there. The [skymp `SkyrimPlatform.cpp` source](https://github.com/skyrim-multiplayer/skymp/blob/main/skyrim-platform/src/platform_se/skyrim_platform/SkyrimPlatform.cpp) was inspected: `JsTick` separates tick/update queues, and `PushToWorkerAndWait` uses a condition variable; useful as a queue distinction, rejected as a direct template for this client because it can stall the frame. [CommonLibSSE-NG `SkyrimVM.cpp`](https://github.com/CharmedBaryon/CommonLibSSE-NG/blob/main/src/RE/S/SkyrimVM.cpp) was inspected: it binds VM singleton and post-render functor queue but does not establish main-thread execution; use the 1.7.104 decompile for the actual job placement. Atlas `systems/main-loop-and-frame-phases.md`, `systems/jobs-tasks-and-threading.md`, `systems/papyrus-vm-internals.md`, `tables/locks.tsv`, and thread classes in `hooks/catalog.json` supplied the wider phase/lock map. In the catalog, `bhkWorld::Update` N77851 is tagged `job-worker:L4.7` and quest stage setters include both `vm-function-message` and `job-worker:L4.2`; those are reasons to keep the generic dispatcher out of concurrent native phases. The catalog's older `EnableFunctor` main-thread label is corrected by the atlas/Papyrus trace: running-frame post-process functors execute on a worker. Lock presence is not evidence that arbitrary actor/scene access from a VM worker is safe.

Reviewer A completed an independent source-only review. It could not access `sk.cmd` or the atlas, so its engine phase claims were not treated as verification. It objected to a wholesale first cut and flagged changed one-frame handoffs, main-thread inline execution and nonrecursive lock re-entry, alternate N36564 callers, menu double-pumps, `bAlwaysActive`, and frame-time cost. The staged plan and per-service audit above adopt those concerns. Its suggestion to leave the whole network receive callback in the VM job is **not adopted**: `TransportService::HandleUpdate` can synchronously deliver packets into engine-facing subscribers, so only an inspected value-only decode stage qualifies. Reviewer B could not start in this sandbox: its launcher tried to write its update-check file and received access denied. Neither reviewer agreement nor this static design validates gameplay behavior.
