# Host-only quest and scene authority (design; no client patch)

Scope: SkyrimSE.exe 1.7.104.0, the current shared-campaign implementation, and the MQ101 failure observed on 2026-09-24. This document is a design for the implementer's separate implementation worktree; it does not claim a working hook or a verified cure. VAs assume image base `0x140000000`; IDs are from the local 1.7.104 Address Library. Query with `C:\Tools\skyrim_re\sk.cmd fn id:<ID>`.

## Decision

The party leader's game is the sole executor of **shared** quest stage items, Papyrus quest fragments, shared scenes, scene actions, and NPC scene packages. The server orders its committed outcomes. Followers receive quest/journal state and a presentation stream, but do not independently drive those shared scripts or scenes. Player-specific scripts (notably each player's character creator) remain local. This is an authority split, not a global Papyrus shutdown.

The server already rejects non-leader quest transactions and keeps epoch/revision ordering. That protects the **network ledger**, not the follower's local engine: a follower can run a fragment and mutate controls, actor packages, globals, or references before its quest update is rejected. Its local `TESQuest::SetStage` hook suppresses some follower-originated stage writes, but `QuestService::OnQuestUpdate` calls `ScriptSetStage` under `ScopedQuestOverride`, allowing a host update to run the follower's native stage-item path. The existing `SceneTimelineService` only observes and logs host/local scene state; it does not prevent a follower scene from advancing.

## Native evidence and boundary map

| Native entry (VA; ID) | Corpus observation | Design consequence |
| --- | --- | --- |
| `TESQuest::SetStage` `0x1403D0DC0`; **25004** | Finds the stage, raises `currentStage` at +0x228, calls `0x1403E19B0`, then marks the quest changed. | Calling this on a follower is **execution**, not a passive stage mirror. |
| Stage processing `0x1403E19B0`; **25252** | Marks the stage-done bit, loops stage items, calls `0x1403E1F60` for each, and can dispatch stage events. | Suppress before this path for shared follower transactions; do not merely block outgoing network messages. |
| Stage-item processing `0x1403E1F60`; **25260** | Evaluates conditions; can complete/fail quests, update objectives, and dispatch stage-item callbacks/events. | A blunt skip loses vanilla side effects. The host must execute them once, then replicate their resulting state by domain. |
| Papyrus quest `SetCurrentStageID` bridge `0x140A5FB50`; **56684** | Ensures quest start and reaches native `TESQuest::SetStage` when the quest is already started; otherwise it queues a start/stage operation. | Cover Papyrus-originated stage writes **and** deferred start/stage operations. The decompiler's native signature is imperfect; confirm calling arguments before hooking. |
| Quest scene update `0x1403D1540`; **25017** | Iterates the quest's scene array at +0x208 and advances playing scenes. | A follower's scene scheduler can diverge even if its quest-stage setter is blocked. |
| Scene phase update `0x1403A7970`; **24126** | Checks playing state +0xB0 and current phase +0xBC, tests phase/action completion, dispatches `0x1403ADE60`, then increments phase. | The host owns phase transitions. A follower must not let this local loop make shared transitions. |
| Scene phase dispatch `0x1403ADE60`; **24305** | Evaluates phase conditions and sends a phase-results callback/event. | A copied phase number is not equivalent to executing or reconstructing scene actions. |
| Scene stop `0x1403A8060`; **24140** | Emits scene-results callbacks, stops actions, clears playing/phase state, and may stop the parent quest. | Stop transitions are authoritative transactions too, not just a boolean mirror. |
| Scene save/load `0x1403A8C60`/**24149**, `0x1403A8EB0`/**24150** | Saves/restores playing, phase, per-action state, and other scene fields. | `isPlaying` + raw phase alone is incomplete for join/recovery; investigate a bounded native state serializer or explicit action-state mirror. Do not feed untrusted network bytes to the load function. |

The local live Papyrus trace recorded `Game::DisablePlayerControls` from `QF_MQ101_0003372B.Fragment_4` at stage 10 on **both** PCs. That is an expected opening lock, not proof of the later stuck lock. Separately, the installed vanilla `mq101questscript.psc` calls `CameraBobStart()` from `PF_MQ101PlayerMoveLineMarker_000F46E4`, `PF_MQ101PlayerToChoppingBlock_00065C94`, and `PF_MQ101PlayerToMarker6_00065C92`. This routine disables controls and sends `IdleWalkingCameraStart`; its matching end routine reverses the camera event. The user's live console test proved `player.sae IdleWalkingCameraEnd` stops bobbing and `epc` restores movement, but **did not prove which package or fragment started the bad instance**. Quest-stage suppression alone cannot be advertised as the fix.

The [CommonLibSSE TESQuest layout](https://ryan.commonlib.dev/TESQuest_8h_source.html) corroborates distinct current-stage, stage-data, objective, and alias structures; the [CommonLibSSE-NG BGSScene layout](https://ng.commonlib.dev/classRE_1_1BGSScene.html) corroborates separate phases, actions, and playing state. Exact 1.7.104 offsets above come from the executable, not those cross-version headers. The [SKSE ObjectReference script](https://github.com/ianpatt/skse64/blob/master/scripts/vanilla/ObjectReference.psc) explicitly notes that a latent `MoveTo` called from a quest fragment can delay completion, illustrating why fragment completion and its later continuation must not be replayed on a follower.

## Authority contract

1. Classify each quest as `Shared`, `PlayerLocal`, or `Unsupported/unknown`. Shared is opt-in during rollout; mod/Creation quest scripts are not presumed safe just because their stage numbers match. MQ101 is shared except for explicitly isolated per-player chargen. Never suppress core local quests outside a party or before the campaign epoch is committed.
2. The leader executes a shared transition in Skyrim. The server accepts one transaction keyed by `{campaignEpoch, questFormId, leaderSequence}` and broadcasts a committed state delta with a monotonically increasing revision. A follower may propose an interaction, but not execute a shared stage/scene transition locally before host authorization.
3. The follower applies the committed **result**, not `TESQuest::SetStage` or Papyrus `SetCurrentStageID`. The replica must include quest running/completed/failed flags, every completed stage bit needed by conditions, current stage, objective states, alias/ref bindings, relevant globals, and active scene/action state. Stage alone is inadequate. Keep a separate canonical campaign ledger for late join, reconnect, and saves.
4. The replica applicator must use an engine-validated passive state path. Directly writing `currentStage` or stage flags is only a candidate: prove change-form persistence, journal refresh, `GetStage`/`GetStageDone` and dialogue-condition visibility, alias coherence, and absence of fragment/event dispatch on 1.7.104 first. If no such path exists, expose a follower-only read facade for conditions/journal and keep the native quest inert; do not silently call the normal setter.
5. Shared scene starts, phase changes, action starts/completions, dialogue speaker/line, and stops are committed from the host. Followers render timing, camera, subtitles, audio, animation, and NPC transforms from host data. They must not let their own scene conditions, action callbacks, AI packages, or local Papyrus stacks advance shared state. A scene's `+0xB0/+0xBC` snapshot is a diagnostic, not a complete replay format.
6. When a follower joins during MQ101, it observes the host cinematic. Its local player must not be assigned to the Helgen scene/cart packages or evaluate the host's package fragments. At the chargen barrier, open only that player's local creator in an isolated transaction; on readiness return to host presentation. Release their character only after the host's verified stage-160 controllable transition. See `INTRO_MQ101_MULTIPLAYER.md`.

## Safe interception plan for the separate hook-host branch

- Add an **observe-only** transaction trace first: native stage entry/exit, stage-item callback scheduling, Papyrus fragment stack identity, scene start/phase/action/stop, local player package changes, `IdleWalkingCameraStart/End`, and ControlMap masks. Correlate by campaign epoch, quest/scene ID, script source, thread, and host sequence. No full Papyrus VM pause; no automatic `epc` during legitimate intro locks.
- Gate shared follower execution at the earliest proven **semantic** boundaries: stage-item dispatch, shared scene scheduler, and NPC/player scene-package assignment. The VM-dispatch hook is a last-resort backstop for already-queued shared fragment stacks, not a blanket native-call filter. Do not block `Game.DisablePlayerControls` globally: RaceMenu and other local systems legitimately use it.
- Drain or invalidate already-queued shared follower stacks when authority changes, using a generation/epoch check at resume. A hook installed after a fragment has begun cannot undo its side effects; joining mid-scene needs a clean baseline or a validated passive-state restoration, not an assumption that the gate retroactively fixed the client.
- Replicate resulting world changes through their owning systems (quest, actor, object, inventory, camera, UI). A quest fragment may call any of these. The host transaction should include causal IDs so duplicate/out-of-order effects are rejected, but native effects should not be re-executed as part of journal replication.
- Promote/demote leader only at a barrier with a checkpointed quest ledger and drained pending scene/fragment work. Revoke the old leader's writer lease before enabling the new one; otherwise two local VMs may commit overlapping actions.

## Acceptance gates

1. In a paired fresh MQ101 run, host/follower logs show exactly one shared stage-item/fragment executor (host), while follower `GetStage`/`GetStageDone`, journal/objectives, and dialogue conditions match host. Follower `Game::DisablePlayerControls` calls arising from MQ101 shared fragments/packages are zero outside its own chargen transaction.
2. Host and follower scene/action records agree by server sequence after a late join and after a phase boundary. A follower never advances a shared phase or starts a shared package without a host commit. The same test covers a scene stop and quest stop.
3. Bob/control-lock regression: after join, respawn, and leaving chargen, record first-person animation state and ControlMap effective/stored masks (`+0x120/+0x124`); both clients move when the host's campaign state says they may. If a lock remains, the trace identifies the exact script/package and transition. No console command is required in a passing run.
4. Reconnect, duplicate packet, reversed packet order, save/load, and leader transfer leave exactly one committed quest transition and no replayed fragment. A modded quest with unknown side effects stays `Unsupported` until classified, not partially synchronized.

## Open proofs before implementation claims

- Identify the exact native stage-item-to-VM scheduling function and callback lifetime after `0x1403E1F60`; the corpus shows the event handoff, while the live VM trace shows the eventual script, but the full causal chain is not yet pinned.
- Prove a passive quest-state applicator, including aliases/objectives and save persistence. No current source function establishes that merely setting `currentStage` is sufficient.
- Confirm whether the follower's bad camera lock is from local package scheduling, a re-entered MQ101 fragment, or a respawn path. The console trial proves the two stuck states, not their origin.
- Validate exact scene/action lifecycle and per-action save/load before treating the scene serializer as a network format.
